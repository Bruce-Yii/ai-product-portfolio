**AI Product Manager**

## 3. 旗舰案例叙事稿

统一叙事结构：

**场景 → 用户问题 → 产品洞察 → 关键决策 → 方案取舍 → 实现与协作 → 验证 → 当前边界与下一步。**

每个案例提供三个阅读深度：
- 10 秒：一句话说明项目、本人角色和价值。
- 1 分钟：问题、洞察、关键决策、交付阶段。
- 3–5 分钟：完整决策过程、备选方案、实现证据、验证和限制。

### 3.1 Personal Context Keyboard｜旗舰 Case 01

#### 10 秒摘要

一个面向 Android 与 Windows 的个人上下文输入法项目。我主导产品定位与跨端架构，将键盘从单一输入工具扩展为个人上下文的采集入口，围绕原始事实、可追溯组织、用户修订和跨 AI 授权使用构建完整产品能力。

#### 1 分钟摘要

**问题：** 用户的长期信息散落在聊天、输入、文件和不同应用中。每次使用 AI 都要重复提供背景，模型记忆又难以让用户确认来源、修订内容和控制使用范围。

**洞察：** 真正值得构建的不是另一个聊天记忆插件，而是用户拥有的 Personal Context Layer。输入法是高频入口，但不应该成为数据和能力的边界。

**关键决策：**
1. 将 Android IME / Windows Capture 视为 Sensor，将 Context Core 独立出来。
2. 原始输入与模型派生内容分层保存，保留来源和时间。
3. 事件、主题和关系是可重建的派生结构，不覆盖原始事实。
4. 用户能够确认、纠错、撤回；模型推断不能自动升级为用户事实。
5. AI Gateway 只向外部模型提供用户明确授权的上下文范围。

**实现：** 主体工程已接近完成，已有 Android IME、中文输入、语音 / ASR 文件链路、Context Store / Recovery、Today / Smartbar、剪贴板、个人词典、备份恢复、打包与自动化回归等实现记录。

**当前阶段：** 接近完成的个人产品实现。正式产品验收尚未通过；真实设备、真实麦克风、arm64、Windows TSF、生产签名与发布仍需逐项完成。

#### 3–5 分钟深读结构

1. **The fragmentation problem**：跨应用、跨设备、跨模型的上下文重复输入与丢失。
2. **The product insight**：从 Keyboard 转向 User-owned Personal Context Layer。
3. **The core abstraction**：Sensor / Raw Facts / Derived Context / User Control / AI Gateway。
4. **The critical decisions**：Local-first、Raw / Derived 分离、来源追溯、用户修订权威、授权边界。
5. **The implementation**：Android IME、输入链路、语音文件处理、Context Store / Recovery、Today / Smartbar、备份恢复与测试。
6. **The validation boundary**：主体实现与自动化回归已有证据；真实设备、麦克风、arm64、Windows TSF、正式验收与发布仍需完成。
7. **What remains**：按 CURRENT-STATE 的真实 Gate 展示，不把未完成项隐藏，也不把它们扩大成主体未实现。

#### 个人责任表述

本人负责产品定位、用户价值定义、跨端架构、关键产品决策、工程推进和验收协调；部分早期模拟器原型及工程执行由 Agent 协助完成，具体代码归属以仓库 commit / 文件记录为准。

#### 禁止表述

- 已正式上架 / 已正式发布。
- 已完成全部真实设备和麦克风验收。
- 已完整支持 Windows TSF 生产输入。
- 已被大规模真实用户验证。
- 将 Agent 协助实现的全部代码说成本人逐行编写。

### 3.2 VIVIC｜旗舰 Case 02

#### 10 秒摘要

VIVIC 是团队打造的多模态卡片助理。我在赛后受邀加入，接手既有产品并推动 Agent 决策链路和产品体验优化，让用户表达能够进入卡片、工具执行和反馈流程。

#### 1 分钟摘要

**问题：** 用户通过语音、文本或图片表达需求后，传统对话容易止于一次回答；信息难以变成持续可用的卡片和后续行动。Agent 工具入口越多，也不意味着用户任务完成得越好。

**洞察：** 产品应该围绕用户任务组织能力，而不是围绕工具数量组织界面。Agent 必须理解意图、选择合适能力、检索已有卡片并给出可理解的执行结果。

**关键决策：**
1. 将体验主线从一次性聊天转向输入、卡片、行动和回执。
2. 收敛重复工具职责，减少选择歧义。
3. 将卡片查找抽象为可复用能力。
4. 通过语义缓存与前缀复用优化重复上下文处理。
5. 区分模型决策、工具执行和真实结果，避免把“调用成功”误认为“任务成功”。

**个人参与：** 本人账号 authored PR #1–#6 和部分 commit，涉及决策链路、工具收敛、卡片查找与缓存相关改造；部分 lead 账号提交及其他成员工作属于团队成果。

**验证：** 有后端部署报告与专项测试记录。11 月 5 日部署报告记录 60 题检查 59/60、API p50 1807ms、缓存命中约 98.8%，并记录 8 条历史单测失败。这些是特定部署和测试快照，不代表线上真实用户成功率或商业 ROI。

#### 3–5 分钟深读结构

1. 产品原始场景与团队既有产品。
2. 用户表达如何转成可持续使用的卡片和行动。
3. Agent 决策链路及工具职责问题。
4. 工具收敛、卡片检索和缓存的关键取舍。
5. 本人 authored PR / commit 与团队交付边界。
6. 部署、专项回归和性能数据。
7. Beta / 登录限制、历史单测失败、部署 SHA lineage 未完全核验及真实用户效果缺失。

#### 个人责任表述

本人在比赛中认识团队，赛后受邀加入；加入后接手既有产品，参与产品体验优化与 Agent 决策链路调整。公开叙事以本人 authored PR / commit 和可追溯工作为个人贡献，团队产品、其他成员提交和竞赛结果明确标注为团队层成果。

#### 禁止表述

- 个人独立打造 VIVIC。
- 将团队竞赛成绩写成个人获奖。
- 将本地 60/60 和线上 59/60 合并。
- 将缓存命中率直接说成成本下降或业务 ROI。
- 把 Beta / 登录访问写成公开正式上线。

### 3.3 AWRP × Linear｜旗舰 Case 03

#### 10 秒摘要

从 AWRP 多 Agent 接力原型和 Linear × Notion 的真实协作实践出发，我将长期项目、执行会话、责任、证据和验收拆分为不同层次，并据此形成 Agent Project OS 的产品定义与架构方案。

#### 1 分钟摘要

**问题：** 多窗口、多 Agent 工作中，执行者和会话经常变化，但项目目标、任务状态、依赖、产物和验收不能随之丢失。仅依赖聊天记录或让 Agent 互相转述，容易造成状态漂移、重复执行和责任不清。

**洞察：** 稳定对象应该是 Project / Task，而不是 Agent 或 Session。执行者可以更换，项目事实与验收标准必须持久化。

**关键决策：**
1. 将 Project / Task 与 Run / Session 分离。
2. 复用 Linear 的任务状态与执行管理能力。
3. 由 Notion 承载长期语义、研究和决策。
4. 由 GitHub / 外部系统提供真实交付状态。
5. 由 ChatGPT 承担总协调、任务设计和独立 Review，Agent 负责执行。
6. 在产品化时优先拆解和复用成熟模块，不重复造 Agent Runtime、工作流引擎和已有基础设施。

**演进：**
- AWRP：历史协议和工程原型。
- Linear × Notion：当前真实使用的项目协作工作流。
- Agent Project OS：基于实际问题和竞品研究形成的独立产品设计，已作设计阶段 GO 判断；G0–G2 有文档交付，G3–G5 尚未完成，产品代码尚未开始。

#### 3–5 分钟深读结构

1. 多 Agent 长期任务为什么容易失去连续性。
2. 从 Agent / Session 中抽离稳定 Project 身份。
3. AWRP 的接力协议和历史原型。
4. 为什么转向 Linear + Notion，而不是继续堆叠自研任务系统。
5. DeepSeek Super-agent 等第三方实现带来的架构启发；明确第三方归属。
6. Agent Project OS 的目标用户、核心对象、系统边界和复用策略。
7. GO 决策、G0–G2 文档成果、G3–G5 未完成和代码未开发的边界。

#### 个人责任表述

本人主导 AWRP 早期协议原型、Linear × Notion 真实工作流改造，以及 Agent Project OS 的产品定位、研究和关键架构取舍。Agent Project OS 当前仍是设计阶段项目，不是已交付产品。

#### 禁止表述

- 已开发完成 Agent Project OS。
- AWRP 是当前生产级平台。
- Linear / Notion 是本人研发的 SaaS。
- 将 DeepSeek、ACP、Pi、OpenClaw 等第三方能力写成本人实现。

## 4. Laya 独立案例册的首页入口文案

**标题：让 AI 决策从模型输出走向可信产品能力。**

简介：

围绕 Laya 从模型能力到开发者真实采用的过程，持续参与产品方向讨论、方案评审、实现协作与上游演进。通过意图保真、决策可信、受控采用和开发者契约四组产品系统，呈现如何将复杂决策能力转化为可验证、可控制、可集成的产品能力。

四组产品系统：

1. **Intent Fidelity｜意图保真**：输入、上下文、路由与集成契约保持用户原意。
2. **Decision Confidence｜决策可信**：评测证据、训练原语和校准结果可检查、可复用。
3. **Controlled Adoption｜受控采用**：阈值、审核、动作与回退边界清晰。
4. **Developer Contract｜开发者契约**：Demo、服务、SDK、CI 与部署体验可预测。

证据表达：
- 以 authored PR、正式 Review、Issue 问题发现和跨贡献者交接分别呈现。
- 明确区分本人实现、本人 Review 建议、他人实现和维护者决策。
- 不使用官方 Collaborator / Maintainer / Co-author 身份。
- PR / Review 数量只作为活动范围快照，不等同独立功能数或业务成效。

## 8. 内容呈现规则

1. 标题先说用户问题或产品变化，不先说框架名。
2. 首段明确项目是什么、用户是谁、本人是什么角色。
3. 技术名词只在解释关键机制时出现；不能用名词堆砌替代产品判断。
4. 数据必须附口径、时间和来源；测试数据不冒充线上业务指标。
5. 团队项目第一屏就说明团队属性与本人加入 / 负责范围。
6. 研究设计、已执行、已验证、接近完成、Draft、HOLD 必须有明确阶段标签。
7. 正文主线先讲问题与决策，证据链接轻量附在相关段落；首页不做证据墙。
8. 允许产品化润色和叙事整合，但不虚构职位、身份、用户、收入、客户、个人贡献或上线状态。
9. 不把一个底层能力自然产生的结果拆成虚假的独立产品功能；可以展示支撑该能力的记录、事件、时间戳和可验证机制。
10. AI 生成图只能用于概念解释和视觉叙事，不能冒充真实 UI、真实数据、代码或实验结果。
