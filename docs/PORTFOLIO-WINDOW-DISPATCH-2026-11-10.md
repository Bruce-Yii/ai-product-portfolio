# 2026-11-10｜作品集 Phase 1–2 并行窗口任务包

**总控：** ChatGPT / W0  
**当前网站基线：** v2.3 preview  
**工作方式：** 三个辅助窗口只读并行；W0 汇总、裁决、形成唯一执行版本。  
**本任务包不授权任何窗口修改网站代码、Notion 正式决策、GitHub 主分支、部署、DNS 或搜索索引。**

## 总控统一约束（所有窗口必须遵守）

- 只做指定范围；不要擅自扩展项目、改网站或创造新方向。
- 研究必须有可访问原始来源、URL、页面日期和核验时间；优先雇主官网、个人作品集原站、真实仓库。
- 区分事实、作者自述、研究者推断和建议；不要把自述指标写成独立审计结论。
- 对项目成熟度明确标记：已执行 / 已验证 / 研究设计 / 规划中。
- 对个人与团队贡献明确分开。
- 不要把高级社招能力要求当成用户已经具备的履历。
- 不要只交一堆链接；必须给出结构化分析、优先级、证据和具体建议。
- 只在自己的窗口返回成果，不要直接修改本仓库或 Notion；W0 统一写回和整合。
- 发现信息缺失时标注“未核实”，不要猜。

## W1｜AI PM 招聘能力矩阵与双层定位研究

### Goal
独立校验并深化当前 AI PM 定位。把 2027 届 / 应届 / 0–3 年岗位的真实门槛，与 3–8 年及更高级 AI PM / Agent PM / AI Platform PM 岗位的进阶要求结合，形成可用于作品集的双层能力模型。

### Scope
1. 收集 2026 年仍有效的中国岗位，优先杭州、上海、苏州、南京；至少覆盖 10 个真实雇主岗位，其中校招 / 0–3 年不少于 6 个。
2. 另收集至少 5 个 3–8 年或 Senior / Lead / Product Owner 岗位，优先官方招聘页；可包含中国和国际企业。
3. 岗位分层：AI PM、Agent PM、AI Platform / Developer Platform PM、AI 应用 / 企业产品 PM。不要把它们混成一个岗位。
4. 提取职责、必备能力、加分项、经验要求、技术深度、业务责任、指标、协作对象。
5. 将能力归并为两层：
   - 基础六项：场景洞察、产品抽象、Agent 设计、技术判断、效果评测、端到端推进。
   - 进阶六项：产品战略与组合管理、业务价值与 ROI、平台化与生态、企业级可靠性与治理、跨组织领导与交付、商业化与 GTM。
6. 标注哪些能力是岗位硬要求、哪些是加分项、哪些只在高级岗位出现。
7. 对当前定位假设“AI 产品经理 / Agent 工作流与 AI 应用产品化”给出 2–3 个定位候选，比较市场覆盖、差异化、证据可展示性和可能误读。
8. 对照候选人的现有项目只做初步映射；没有证据的地方标记待 W3 审核。

### Non-scope
- 不改网站文案或首页。
- 不替用户决定最终定位。
- 不使用过期岗位或招聘聚合站作为唯一证据。
- 不把高级岗位职责包装成候选人已完成的经历。

### Required output
1. 岗位样本表（公司、岗位、地点、经验、发布日期 / 页面状态、URL）。
2. 基础六项 × 进阶六项能力矩阵（出现频率、层级、典型证据）。
3. 岗位分层和能力差异分析。
4. 2–3 个定位候选及推荐理由。
5. 对作品集首页和案例应如何证明这些能力的建议。
6. 资料限制与未核实项。

### Acceptance
- 每个核心结论至少有 2 个独立岗位来源支持。
- 至少 15 个岗位样本，校招 / 0–3 年不少于 6 个，高级岗位不少于 5 个。
- 每个岗位注明经验门槛，不能混用。
- 关键结论能追溯到原始岗位描述。

## W2｜优秀 PM / AI PM 作品集真实网站 UX Benchmark

### Goal
研究真实优秀作品集的内容呈现和用户体验，尤其是招聘方如何从首页自然读到案例、证据和联系入口。研究范围允许近 1–2 年，但优先 2025–2026 年仍可访问的网站。

### Starting references
- https://kibitkin.com/
- https://mstublefield.com/
- https://mstublefield.com/case-studies
- https://kireetivarma.me/
- https://davidjonesai.com/
- https://www.priankr.com/
- https://elenacalvillo.com/
- https://www.geraldyuan.com/zh/
- https://aipmportfolio.vercel.app/
- https://simonpan.com/
- https://www.marco.fyi/
- https://www.dotconor.com/
- https://mikematas.com/
- https://www.raffi.town/

### Scope
1. 至少实地浏览 8 个 PM / AI PM 网站，不能只看文章摘要。
2. 另外选 3–5 个设计作品集作为视觉 / 交互参考，明确它们不是 PM 信息架构标准。
3. 检查：首页首屏、项目顺序、卡片信息、主导航、案例页面结构、证据链接、联系入口、返回路径、移动端。
4. 对至少 5 个网站记录真实阅读路径：打开首页 → 看见什么 → 点击 / 滚动什么 → 进入哪个案例 → 如何返回 / 继续。
5. 如果环境允许，保存 1440px 和 390px 的关键页面截图；不能截图就记录实际观察，不得伪称完成截图。
6. 找出值得吸收的呈现形式：结果首屏、问题型标题、案例阶段、左右图文、可运行原型、交互式 demo、写作索引、职业轨迹等。
7. 同样记录不值得复制的做法：多入口、复杂筛选、过度滚动、炫技导航、案例堆砌、模糊角色等。
8. 将观察结果映射到本网站七个方向，尤其是 P0 阅读路径和案例叙事。

### Non-scope
- 不做网站代码修改或 Figma 重设计。
- 不把设计师作品集的 UX 评审数据直接当成 AI PM 招聘数据。
- 不以个人审美代替招聘方任务。
- 不复制他人的视觉风格。

### Required output
1. 网站样本矩阵（URL、职业阶段、目标岗位、更新时间 / 核验日期）。
2. 每个样本的首页与案例 UX 观察。
3. 至少 5 条可迁移的呈现模式及其适用条件。
4. 至少 5 条应避免的模式及原因。
5. 本网站的建议阅读旅程和页面层级。
6. 视觉 / 交互参考板：每个参考说明“借什么、为什么、如何适配”，不只贴链接。

### Acceptance
- 至少 8 个 PM / AI PM 真实网站被实际打开并分析。
- 至少 5 条建议有具体网站观察作为依据。
- 每条建议说明对招聘方阅读任务的作用。
- 设计师案例和 PM 案例明确分开。

## W3｜个人项目 / 案例 / 证据与个人责任审计

### Goal
建立作品集的事实底座，回答哪些项目最能证明基础六项与进阶六项能力，哪些值得旗舰展示，哪些只适合作为 Contribution 或暂不公开。

### Source scope
- Notion「🧠 我的第二大脑」中的作品集项目、Case Brief、开源贡献和素材记录；
- GitHub 个人仓库与参与仓库、PR、Issue、Review、Commit；
- 现有作品集仓库 v2.3 和已链接的项目官网；
- 可公开访问的团队 / 产品网站。
若无法访问某一数据源，明确报告访问限制，不得猜测或以搜索摘要替代证据。

### Candidate assets to inspect
Personal Context Keyboard、VIVIC、AWRP × Linear / Agent Project OS、Laya、Google ADK、Dify / RAGFlow / OpenClaw 等开源贡献、Agent Evaluation Lab，以及 Notion 中可能有价值的其他案例。此清单是审计范围，不代表全部都应上站。

### Scope
对每个候选项目 / 案例记录：
1. 目标用户 / 场景 / 原始问题；
2. 用户本人发现的产品问题或关键洞察；
3. 产品决策、方案取舍、明确放弃项；
4. 个人实际负责内容；
5. 团队 / 维护者 / 其他参与者的责任边界；
6. 当前成熟度：已执行 / 已验证 / 研究设计 / 规划中；
7. 可核验的 PR、Issue、Review、Commit、原型、真实页面、测试或文档；
8. 可证明的基础能力和进阶能力；
9. 结果指标的定义、来源和限制；
10. 公开风险、保密边界和面试追问难点。
对相似贡献进行合并判断：若多个 Issue / PR / Review 构成同一个产品故事，不要强行拆成多个 Case。

### Non-scope
- 不改案例文案、不更新 Notion、不改 GitHub 文件。
- 不替用户虚构数据、身份、商业效果或责任范围。
- 不因某个项目有很多 PR 就默认它是旗舰案例。
- 不把规划中的产品写成已上线产品。

### Required output
1. 全部候选案例 / Contribution 清单。
2. 个人与团队责任矩阵。
3. 基础六项 × 进阶六项证据映射。
4. 每项证据来源和成熟度。
5. 旗舰 / 支撑 / Contribution / HOLD 初步建议及理由。
6. 最值得优先写成深度案例的 3–5 个候选。
7. 需要 W0 / 用户判断的事实缺口（只列真正无法从资料核实的内容）。

### Acceptance
- 所有旗舰候选至少有两类独立证据，或明确说明为何只有一种。
- 个人贡献和团队成果可区分。
- 每个数字都可追溯，不能把估算当结果。
- 所有成熟度和公开风险明确标注。

## W0 总控验收规则

1. 先分别 Review W1 / W2 / W3 的证据和结论，不直接采信自报“完成”。
2. 检查三个任务是否互相矛盾、重复或使用不同口径。
3. 将岗位能力、作品集 UX 模式和个人证据交叉，形成唯一能力定位与案例组合建议。
4. 先输出决策包，再更新策略 / Notion / 网站。
5. 在 Phase 1 / 2 未验收前，不开启大规模视觉改版。
